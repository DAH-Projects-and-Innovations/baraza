# Sprint 04: database, migrations and versioned minutes

Branch: `thierry-sprint04`. Scope: #50, #51, #53 and regression coverage for
#126, #127 and #77. The minimal prerequisite test infrastructure for #49 is
included. The full Meeting/transcript model in #52 remains a separate dependency.

## Database lifecycle (#50)

`baraza/db/base.py` declares one `Base` with named primary keys, unique, foreign
key and check constraints. `db/models.py` registers all mapped models for Alembic.
`db/session.py` owns the async engine and `async_sessionmaker` per API/worker
process. Engines are disposed on shutdown, including when Vexa is disabled.
Stores use that engine; requests do not construct their own connection pools.

`SessionDep` injects a transactional `AsyncSession`. It commits before the response
is sent and rolls back on exceptions. Services receive that session and the
caller owns its outer transaction. The SQLite test driver enables explicit BEGIN
and foreign keys so savepoint and rollback tests exercise real transaction behavior.

## Migrations (#51)

The async Alembic environment uses `Base.metadata` and `BARAZA_DATABASE_URL`.
No application store uses `create_all`. Two revisions are provided:

1. `0001_capture_baseline`: existing meetings, Vexa handles and transcript segments.
2. `0002_minutes_versions`: minutes and their revisions, with JSONB on PostgreSQL
   and JSON on SQLite for fast tests.

On an empty database, `docker compose up --build` runs the one-shot `migrate`
service (`alembic upgrade head`) after Postgres is healthy. API and worker wait
for its successful completion. A migration failure prevents them from starting.
For an existing checkout, rerun `docker compose run --rm migrate` when deploying
new migrations before recreating API/worker; retain a database backup.

Local development from `backend/`:

```bash
uv run alembic upgrade head
uv run alembic check
uv run alembic revision --autogenerate -m "Describe the schema change"
```

Review generated revisions before applying them. CI starts Postgres/Redis,
runs `alembic upgrade head`, then `alembic check`, then tests. An unmigrated
model change fails CI. A local test also introduces a temporary model and confirms
that drift detection rejects it; it tests downgrade and upgrade again afterward.

### Existing databases created before Alembic

The baseline creates tables and intentionally does not silently stamp an existing
schema. An old database containing unversioned tables will stop with an existing
table error. Back it up and inspect it before preparing an adoption migration.
Legacy autogenerated constraint names may differ from the new naming convention.
Do not reset a shared volume or stamp `head` to bypass this: it can conceal schema
differences and skip the minutes migration. The included automated path is for
empty databases or databases already tracked by these revisions.

## Minutes model and service (#53)

`minutes` stores one current document per meeting: draft/validated status,
validated `Minutes` JSONB content, template, model name, prompt version, optimistic
version counter, validator and validation timestamp. Foreign keys tie minutes
to the existing meeting table and revisions to minutes. Database checks enforce
valid statuses, positive versions and consistent validation metadata.

`minutes_revisions` stores every saved version, including initial generation
and explicit validation: content, provenance, status, actor and UTC timestamp.
`MinutesService` provides `create_draft`, `save_draft`, `validate`, `get` and
`revisions`. Supply a trusted actor identifier and the version the user reviewed.
Draft creation moves the meeting from `processing` to `draft_ready`; validation
moves it to `validated`, using the existing state machine. Meeting transition,
document and revision are written in one transaction/savepoint.

Updates compare both version and draft status in SQL. A stale edit raises
`MinutesConflict`; validated documents reject edits and repeated validation with
`ValidatedMinutesImmutable`. A failure updating the meeting also rolls back the
document and revision, even when the caller catches the exception. Successful
validation increments the version and records the final immutable snapshot.

Example integration for the generation pipeline:

```python
from baraza.core.minute_versions import MinutesService

async with database.sessions() as session, session.begin():
    stored = await MinutesService(session).create_draft(
        meeting_id, generated_minutes, actor="minutes-worker",
        template="standard", model_name=settings.llm_model, prompt_version="v1",
    )
```

The caller supplies real generation provenance rather than guessed defaults.
Editing integrations call `save_draft(..., actor=trusted_user_id,
expected_version=reviewed_version)`; validation uses the same version requirement.
`GET /meetings/{meeting_id}/minutes` returns the existing frontend `Minutes` schema
and a version ETag; missing documents return 404. Generation itself and wiring
the placeholder `generate_minutes_task` are still part of the LLM integration.

The existing meeting identifiers remain strings to preserve the capture contracts.
#52 still owns the full Meeting metadata, UUID model, transcript document and
participants. This work does not claim that dependency is complete.

## Real integration tests (#49 prerequisite)

The test database role needs `CREATEDB`: tests create a randomly named database
per test session, migrate it, and drop only that database afterward. Transactional
fixtures roll back per test. The concurrency and Vexa tests use independent
committed sessions inside the disposable database. Tests are marked `integration`
and skip when the explicit test service URLs are absent. Configured but unavailable
services fail the tests rather than silently skipping.

Start only the small test services from the repository root:

```bash
docker compose -f docker-compose.test.yml up -d --wait
cd backend
BARAZA_TEST_DATABASE_URL=postgresql+asyncpg://baraza_test:test-only@localhost:15432/baraza_test \
BARAZA_TEST_REDIS_URL=redis://localhost:16379/15 \
uv run pytest -m integration
```

The test Compose file publishes only loopback ports and uses an ephemeral
Postgres tmpfs. To stop it, run `docker compose -f docker-compose.test.yml down`
from the root. It does not use the application's database volumes.
To run fast checks without service dependencies:

```bash
cd backend
uv run pytest -m 'not integration'
uv run ruff check .
uv run ruff format --check .
uv run mypy src
```
